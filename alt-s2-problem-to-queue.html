Alternatives card

Frame the problem and build the queue

  • Workflow step: S2
  • Slot: Day 1, in the 15:00 block

Pocock's way

Pocock gives the agent the problem, asks for a reproduction first and triages each issue into a queue.

  • Give the problem, not file names. The agent explores the code for facts. You decide only what it cannot look up.
  • Reproduce before any fix. The agent first shows the failure on current code. In the lab, from one nightly log line, it writes a failing test.
  • Triage with the triage skill. Each issue gets a category label, bug or enhancement. It gets one of five state labels, such as needs info or ready for agent.
  • Write an agent brief before an issue is ready. Its headings are Category, Summary, Current behavior, Desired behavior, Key interfaces, Acceptance criteria and Out of scope.
  • Record what you refuse. A .out-of-scope folder holds one file per rejected idea. The unattended runner takes only ready-for-agent issues.

What poteto does instead

poteto's bots watch outside channels, and a bot tries to reproduce each bug report on a cloud computer.

  • Context, not control. poteto states the intent and coordinator agents split the work.
  • Bots on outside channels. Bots watch Slack, X, email and Linear. One checks X mentions about every 30 minutes and groups repeats, such as five users reporting the same bug.
  • Reproduce in the cloud. A bot called Benny reproduces each bug report on a cloud computer. It can find the bug already fixed on main. Agents rule out the user's setup, data or a missing dependency.

What Theo does instead

Theo writes problem-first kickoff prompts. Reports become threads in an inbox, and bugs become GitHub issues.

  • Problem first. "I bring in the agent when I start thinking so we can talk it out."
  • A kickoff prompt in parts. It names who is affected, firm priorities, what he does not know and one clear ask. It gives an out: "If you see a simple fix ... stop and let me know."
  • Threads as an inbox. He settles them like inbox zero. A phone prompt for a user's screenshot: "Fix this. Test it. Record a video showing it works now and link me the PR when you're done."

Which target would justify switching

At this step the targets differ on who turns a request into a plan.

  • Pocock's way fits the targets Supervised pairing, Planned backlog delegation and Risk-tiered platform. In each, an interview turns the request into a spec and tickets, which you meet on Day 2.
  • Switch to poteto's way if your target is Environment-first autonomy. It needs a funded platform team and product people who can state intent. It costs plans that are not kept.
  • Switch to Theo's way if your target is Evidence-gated agent merge. It needs fast CI, a staged release, a quick revert and senior engineers who judge evidence. It costs a thin paper trail for plans, which live in threads and HTML files in place of tickets.
