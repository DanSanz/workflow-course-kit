Steps

Part 1, the check command

  1. Part 1. Ask for the check command. Allow the build and test commands it asks to run.

    One command that builds the code and runs the fast tests lets you and the agent check every change the same way. Expect a script that stops at the first failure and exits with that code.

    Python 
    Write scripts\check.ps1 for Windows PowerShell 5.1. It builds the code and runs the unit and module tests. It stops at the first failure and exits with that code, or 0 when all pass. Leave out the acceptance tests. Run tests/spark only with a -Spark switch.
    .NET 
    Write scripts\check.ps1 for Windows PowerShell 5.1. It builds src/MemberIngestion.Job, then runs the tests in tests/MemberIngestion.UnitTests and tests/MemberIngestion.ModuleTests. It stops at the first failure and exits with that code, or 0 when all pass. Do not build the solution or the acceptance tests.

  2. Run it yourself, then let the agent break a test and restore it. You see 0, then not 0, then 0.

    A broken test shows that the check fails when a test fails, and passes again once the test is restored.

    powershell -ExecutionPolicy Bypass -File scripts\check.ps1; $LASTEXITCODE
    Break one assertion in a unit test on purpose. Run scripts\check.ps1 and tell me its exit code. Then restore the test with git restore and run the check again.

Part 2, the setup skill

  1. Part 2. Type /clear, then run the setup skill and answer its three questions.

    The skills do not know your tracker, your labels or your doc layout. This skill records them in three files under docs/agents/.

    Pick GitHub on routes A and B or local markdown on route C, the default labels, AGENTS.md whatever the skill suggests, and origin, your own repo, for issues. On A and B, add the labels anyway, because the skill may make only four of the five.

    /setup-matt-pocock-skills
    "needs-triage","needs-info","ready-for-agent","ready-for-human","wontfix" | % { gh label create $_ --force }

Part 3, pointers in AGENTS.md

  1. Part 3. Type /clear and ask for pointers. Keep the GLOSSARY.md pointer for part 5.

    Pointers keep AGENTS.md short. Each fact stays in its own file, and the pointer sends the agent there in one step. Expect an AGENTS.md of about 20 lines, with the pointers above the Agent skills block.

    /writing-for-agents Extend AGENTS.md with pointers, not prose: run scripts\check.ps1 to build and test, the standards are in docs/standards.md, the runbook is docs/runbook.md, the domain terms are in GLOSSARY.md. Say the README test command fails. Keep the Agent skills block.

Part 4, the rule about feed dates

  1. Part 4. Find the rule about feed dates in docs/standards.md, and check that AGENTS.md points to the file. You are done when you can name the rule.

The question before the glossary

  1. Stop with the trainer, before the glossary. Save your stack's question outside the repo.

    You ask the agent this question now and again after the glossary, then compare the names in the two answers. The command saves it in C:\course\question.txt.

    Python 
    Set-Content C:\course\question.txt 'An employer pays its September contributions for one payroll on 30 October. It has not paid a second payroll at all. A third row has a payment date that cannot be read. What does tonight''s contributions run report, and to whom? Answer in plain words.'
    .NET 
    Set-Content C:\course\question.txt 'An employer sends its November member file. Two people in it started work this month. One row has one more column than the contract allows. What does tonight''s job do with the file, and what do Employer Relations get? Answer in plain words.'

  2. Ask it in a new session and save the answer.

    The answer in before.txt shows the names the agent uses before the glossary exists.

    Claude Code 
    claude -p (gc C:\course\question.txt -Raw) > C:\course\before.txt
    GitHub Copilot 
    copilot -p (gc C:\course\question.txt -Raw) -s > C:\course\before.txt

    The answer has no right wording. Mark the names it uses for employers, files, rows and members.

Part 5, the glossary

  1. Part 5. Type /clear, then start the glossary.

    A glossary gives you and the agent one word for each thing in the repo, so the agent's output drifts less.

    The skill may write 10 terms, then ask questions. Answer as the code works today, in its words, and leave out what it lacks. Then type stop here.

    /domain-modeling Start GLOSSARY.md with the 10 core terms of this repo. Look for things that the code and the docs call by several names. Challenge me where a term is fuzzy.

    Check two definitions against the code.

    Late in this part, redo step 7 but save to after.txt. Comparing the two answers shows whether the glossary changes the names the agent uses.

    Claude Code 
    claude -p (gc C:\course\question.txt -Raw) > C:\course\after.txt
    GitHub Copilot 
    copilot -p (gc C:\course\question.txt -Raw) -s > C:\course\after.txt

    Read both, and note the names each uses for the same things. Count your glossary's terms in the second. If you see no change, do nothing.

The artefact you leave in the repo

  • The check command scripts\check.ps1, which builds the code and runs the fast tests.
  • The skills configuration in docs/agents/, which is issue-tracker.md, triage-labels.md and domain.md.
  • A short AGENTS.md with the Agent skills block and pointers to the check, standards, runbook and glossary.
  • GLOSSARY.md with at least 10 terms, each with a meaning and the names to avoid.

Run both in the repo root. They check the four artefacts and the two answer files.
